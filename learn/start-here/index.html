直接答案

这个学习站帮助你建立一套可以迁移到 vLLM、SGLang、TensorRT-LLM、OpenVINO 或自研推理服务的优化方法。重点不是背参数，而是学会回答三个问题：瓶颈在哪里，应该在哪一层动手，改完以后怎样证明它真的更好。

建议依次学习：

先划清项目边界

当前工作区只有 ARCHITECTURE.md 和这个学习站，没有可运行的推理引擎源码。

ARCHITECTURE.md 明确把“自研基础模型推理运行时”列为非目标。它描述的是一个本地优先的学习引擎，模型运行时被隔离在 RuntimePort 之后。因此本网站中的 CPU/GPU 集群功能是通用推理工程知识，不是对当前目录已有实现的声称。

证据状态：

  • verified：由当前文件、实际构建结果、官方文档或论文直接支持。
  • inferred：从已验证事实推导出的设计建议，会明确标注。
  • unknown：还缺模型、硬件、流量或运行结果，不能下结论。

你将学到什么

第一阶段：识别瓶颈

先理解 Prefill、Decode、KV Cache、TTFT、TPOT 和吞吐。没有这一步，很容易发生“tokens/s 上升了，但用户感觉更慢”的假优化。

第二阶段：选择硬件路径

CPU 优化重点是内存局部性、线程预算、量化内核和请求级扩容。GPU 优化重点是显存、批处理、KV Cache、并行通信和集群拓扑。

第三阶段：用实验做决策

优化不是功能开关清单。同一个开关可能提高总吞吐，却损害首 Token 延迟或 P99。最后一章会给出固定工作负载、单变量实验和验收表。

一条贯穿全站的执行链

客户端请求
  -> 路由和准入控制
  -> 调度器组批
  -> Prefill 计算
  -> KV Cache 分配或复用
  -> Decode 逐 Token 生成
  -> 流式返回
  -> 指标、错误和容量反馈

每一种优化都应该能落到这条链的某个位置。说不清优化修改了哪一段，通常也就说不清它为什么有效。

开始前保留的未知项

目前还不知道你的目标模型、CPU/GPU 型号、节点间网络、输入输出长度分布，以及最重要的 SLO。它们不会阻止学习，但会阻止我们宣布某个配置是“最优配置”。
