CPU 集群推理优化

NUMA、线程、量化、批处理和请求级扩容如何协同

直接答案

CPU 推理的优化顺序通常是：先保证 NUMA 本地性和线程不超卖，再使用匹配硬件的量化内核，然后通过连续批处理与请求级副本扩容。只有模型无法放进单机或单个 NUMA 域时，才值得承担跨节点模型并行的通信成本。

CPU 为什么容易卡在内存

模型推理需要反复读取大量权重。CPU 的计算核心可能很多，但如果线程跨 Socket 读取远端内存，或者多个线程池争抢相同核心，核心会等待数据而不是执行有效计算。

NUMA 机器中，每个 CPU Socket 更快地访问自己的本地内存。PyTorch 官方调优指南建议把推理实例绑定到单个 NUMA 节点，以减少跨节点内存访问。PyTorch Performance Tuning Guide

单机上的五个功能

1. Topology Profiler

启动时读取 Socket、NUMA node、物理核心、逻辑核心、内存容量和可用指令集。这个结果应该成为实例规划输入，而不是依赖固定核心编号。

2. Replica Planner

一个常见布局是每个 NUMA node 一个模型实例：

双路 CPU 服务器
  ├─ NUMA 0：模型副本 A + 本地核心 + 本地内存
  └─ NUMA 1：模型副本 B + 本地核心 + 本地内存

它用重复权重换取内存局部性与请求并行。模型太大、单个 NUMA 域装不下时，才考虑跨域执行。

3. Thread Budget

需要区分：

  • intra-op：一个算子内部并行，例如矩阵乘法。
  • inter-op：多个独立算子并行。
  • 服务线程：HTTP、Tokenization、调度、日志和监控。

把所有物理核心都交给 OpenMP，可能让网络和调度线程饿死；每个请求都创建自己的大线程池，又会产生严重超卖。ONNX Runtime 提供 intra-op、inter-op、线程旋转和亲和性控制，并建议在 NUMA 系统上实测不同绑定策略。ONNX Runtime Thread Management

4. Quantized Kernel Selector

量化减少权重体积和内存流量；如果 CPU 支持 VNNI、AMX 或相应 dot-product 指令，还能使用更高效的整数矩阵内核。

但必须同时验证：

  • 模型精度是否满足要求。
  • 实际算子是否进入量化内核。
  • 是否发生反量化或 CPU fallback。
  • 批次和形状是否适合该内核。

ONNX Runtime 文档明确说明量化收益同时来自计算和内存，并列出 CPU 上的 U8U8、U8S8、S8S8 等格式。ONNX Runtime Quantization

5. Cache and Admission Budget

KV Cache 容量决定允许多少并发和多长上下文。服务应在接收请求前估算缓存需求，并选择：

容量足够 -> 调度
暂时不足 -> 有界排队
超过硬限制 -> 明确拒绝

不能等到内存耗尽后依靠进程崩溃恢复，也不能静默缩短用户上下文。

从单机扩展到 CPU 集群

CPU 集群优先做请求级数据并行：

请求
  -> 前缀感知负载均衡器
  -> 节点 A / 节点 B / 节点 C
  -> 节点内 NUMA 副本
  -> 本地 KV Cache

每个节点拥有完整模型，节点间不需要为每个 Transformer 层同步。它适合独立请求多、模型能放进单节点的情况。

为什么路由不能只看连接数

两个副本连接数相同，不代表剩余容量相同：

  • 一个副本可能处理长上下文，KV Cache 已接近上限。
  • 一个副本可能缓存了请求共同的 system prompt。
  • 一个副本可能有很多即将完成的 Decode 请求。

因此路由输入至少应包含队列长度、估算 Token 数、KV Cache 使用率和前缀命中机会。

何时考虑跨节点模型并行

只有以下情况值得进入：

  • 模型权重或目标 KV Cache 无法放进单节点。
  • 低并发单请求延迟无法通过量化和内核优化达标。
  • 节点间网络延迟和带宽经过测量，足以承担同步。

普通以太网上的高频张量同步可能抵消增加 CPU 的收益。此时需要把通信时间单独计入每层或每 Token 的火焰图，而不是只看总 CPU 利用率。

推荐的服务边界

以下是一个 inferred 参考设计：

组件 状态所有权 失败时行为
Topology Profiler 硬件拓扑快照 无法识别时拒绝自动绑定
Replica Planner NUMA 与实例映射 容量不满足时启动失败
Thread Budget 每实例核心预算 检测超卖并报警或拒绝配置
Admission Controller 请求 Token 与内存预算 有界排队或明确 429/503
Prefix-aware Router 副本负载和缓存位置 路由状态不可用时不声称缓存优化生效
Metrics Exporter TTFT、TPOT、队列、内存 关键指标缺失时基准无效

常见失败模式

  • 只看 CPU 利用率；100% 可能代表线程忙等或内存停顿。
  • 线程数等于逻辑核心数；超线程对内存带宽受限推理不一定有益。
  • 两个实例共享所有核心；线程池互相抢占。
  • 模型量化了，但运行时大部分算子落回浮点路径。
  • 扩到多节点后平均吞吐增加，却没有检查 P99 和单请求成本。

自己动手实验

在同一台双路 CPU 机器上固定模型、输入输出长度和并发，比较：

  1. 一个实例跨两个 NUMA node。
  2. 一个实例绑定 NUMA 0。
  3. 两个实例分别绑定 NUMA 0 和 NUMA 1。
  4. 第 3 项再增加 INT8 或 INT4 量化。

记录 TTFT、TPOT、总吞吐、内存带宽、远端 NUMA 访问和每个实例的核心占用。不要同时改变线程数、量化和批次，否则无法判断收益来源。
