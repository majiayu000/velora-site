GPU 集群推理优化

连续批处理、Paged KV Cache、DP/TP/PP/EP 与阶段分离

直接答案

GPU 集群优化应遵循：先把单卡调度和 KV Cache 做好，再用数据并行增加副本；模型装不下或低并发延迟不达标时，再引入张量或流水线并行；MoE 模型才重点考虑专家并行；长 Prompt 与交互式 Decode 冲突明显时，最后评估 Prefill/Decode 分离。

更多 GPU 并不自动等于更快。并行会引入通信、同步、气泡和更复杂的故障域。

单 GPU 先解决四件事

连续批处理

静态批处理会等待一整批请求全部结束。LLM 请求输出长度不同，短请求完成后留下的空位会浪费 GPU。

连续批处理让调度器在每个迭代重新选择活动序列：

迭代 1：[A, B, C]
迭代 2：A 完成 -> [D, B, C]
迭代 3：C 完成 -> [D, B, E]

它提高利用率，但批次和 Token 预算越激进，单个请求排队与抢占风险越高。

Paged KV Cache

KV Cache 按固定大小块管理，不要求每个请求预留一整段连续显存。这样能减少碎片，并让请求随生成逐步获得块。

调度器必须和缓存管理器共同决策。TensorRT-LLM 的运行时会预分配分页 KV Cache 池，并按缓存容量和调度策略接纳请求。TensorRT-LLM Memory Usage

Prefix Cache

如果多个请求共享 system prompt、文档前缀或多轮历史，可复用已经计算的 KV Cache，主要降低重复 Prefill 和 TTFT。

缓存命中不仅依赖是否开启功能，也依赖路由。把相同前缀的请求发到没有对应缓存的副本，就失去了收益。vLLM 的数据并行文档也指出，每个 DP engine 有独立 KV Cache，负载均衡应考虑缓存状态。vLLM Data Parallel Deployment

Chunked Prefill

长 Prompt 的 Prefill 可能占据一次很大的计算预算，使已经在 Decode 的交互请求等待。切块后，调度器能把一部分 Prefill 与 Decode 混合执行。

它通常改善尾延迟公平性，但块太小会增加调度开销，块太大又无法消除阻塞。

四种并行方式

方式 如何拆 最适合 主要成本
DP 数据并行 每组 GPU 放完整模型，不同组处理不同请求 模型能装下，提高总吞吐 权重与缓存重复
TP 张量并行 一层矩阵切到多张 GPU 单卡装不下，节点内高速互联 每层集合通信
PP 流水线并行 不同层放到不同 GPU 跨节点或模型非常大 流水线气泡和阶段不均
EP 专家并行 MoE 专家分布到不同 GPU MoE 模型 All-to-All 与负载不均

vLLM 支持 TP、PP、DP，并且每个 DP rank 拥有一个 engine core；GPU worker 数由 TP × PP 决定。vLLM Architecture Overview

一个可操作的选择树

模型能装进一张 GPU？
  ├─ 能
  │   ├─ 单请求延迟达标 -> 优先 DP 扩吞吐
  │   └─ 单请求延迟不达标 -> 先查内核/量化/调度，再小范围测试 TP
  └─ 不能
      ├─ 单节点多卡能装下 -> 优先节点内 TP
      └─ 单节点仍装不下 -> 评估 PP 或跨节点 TP，必须测通信

模型是 MoE？
  └─ 是 -> 再评估 EP 和专家负载均衡

TP 尽量限制在 NVLink/NVSwitch 等高速互联域内。跨节点 TP 每层都可能触发通信，对网络抖动非常敏感。PP 降低了同步频率，但可能产生阶段气泡。

Prefill/Decode 分离

Prefill 更适合大批量矩阵计算，Decode 更强调稳定的逐 Token 延迟。阶段分离允许：

长 Prompt
  -> Prefill GPU 池
  -> 传输 KV Cache
  -> Decode GPU 池
  -> 流式输出

收益是两个池可以分别选择 GPU 类型、并行度和扩容策略；代价是 KV Cache 传输、路由和生命周期协调。

TensorRT-LLM 支持使用 MPI、UCX、NIXL 等后端，通过 RDMA/NVLink 传输，并可把 KV 传输与其他请求计算重叠。TensorRT-LLM Disaggregated Serving

阶段分离更适合长输入、中等输出且 Prefill 干扰严重的流量。短 Prompt 或网络较慢时，传输成本可能超过收益。

量化和投机解码放在哪里

量化

可以量化权重、激活或 KV Cache。它可能带来：

  • 模型可以放入更少 GPU。
  • 同一显存容纳更多 KV Cache。
  • 匹配硬件内核时提高吞吐。

但硬件支持随格式和架构变化。应以当前框架兼容表和实际 profile 为准，不能看到 FP8/INT4 就默认更快。

投机解码

小 draft 模型先提出多个候选 Token，大模型一次验证。接受率高时，可以减少大模型串行 Decode 步数；接受率低时，只增加额外计算。

vLLM 的 Speculators 文档把它定义为不改变目标分布的加速方式，但是否有收益仍依赖 draft 成本、接受率和当前设备是否计算受限。vLLM Speculators

集群中的状态与故障

状态 推荐所有者 关键故障
请求队列 API/调度层 无界排队导致 P99 爆炸
KV Cache 单个 engine/rank 路由错位导致命中消失
模型权重 GPU worker/rank group rank 不一致或加载失败
并行组 分布式执行器 集合通信超时、部分节点退出
SLO 与准入 服务控制层 只扩队列、不拒绝过载

分布式执行中不能静默移除一个 rank 后继续声称同一个并行组可用。启动配置、模型版本、量化格式和通信拓扑不一致时，应整体拒绝该副本进入服务。

自己动手实验

在同一台多 GPU 节点上，固定模型、数据集和请求率，比较：

  1. 单 GPU 基线。
  2. 单副本 TP=2。
  3. 两个独立 DP 副本，每个单 GPU。
  4. 第 3 项开启 Prefix Cache。
  5. 如果长 Prompt 明显干扰 Decode，再测试 Chunked Prefill。

如果模型单卡可放下，第 2 项与第 3 项最值得比较：TP 可能影响单请求延迟，DP 更可能提升总吞吐。最终结论必须同时看 TTFT、TPOT、P99、显存和通信时间。
